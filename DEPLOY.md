# Deploying Notesy

Notesy is a small Django + HTMX notes app. This document covers how it goes from a commit on `main` to a running service on AWS, either on **ECS Fargate** or on **EKS** (both paths are built and switchable), the decisions made along the way, and how to operate it.

For everything that broke during the build and how it was diagnosed, see [CURVEBALLS.md](CURVEBALLS.md).

---

## 1. What was built

### Milestone 1: Containerize

- **Multi-stage `Dockerfile`**
  - Stage 1 (Node 20) typechecks and builds the TypeScript bundle.
  - Stage 2 (Python 3.12 slim) runs the app. Node isn't in the final image.
  - The app runs as a non-root user (`app`, uid 1000).
  - `collectstatic` runs at build time so WhiteNoise can serve static files.
- **`entrypoint.sh`**
  - Runs `migrate` on every container start, then `exec`s the command, so gunicorn gets stop signals directly.
  - Migrations live in the image, so they run the same way under Compose, ECS and Kubernetes.
- **`.dockerignore`** keeps `.env`, `.git`, local builds and SQLite files out of the image.
- **`docker-compose.yml`**
  - App plus Postgres 16, with a `pg_isready` healthcheck. The app waits for `service_healthy`.
  - Seeding the `demo/demo` user is local-only.
- **`notesy/settings.py` (ticket NOTESY-101)**
  - Config comes from the environment: `DJANGO_SECRET_KEY`, `DJANGO_DEBUG` (off by default), `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, `DATABASE_URL`.
  - With `DEBUG` off, the app refuses to start if the secret key or database URL is missing, so misconfiguration fails loudly instead of silently falling back to SQLite.
  - Sessions are stored in the database.
- **Gunicorn** runs `gthread` workers (3 workers × 4 threads), so idle or slow connections don't block a whole worker.

### Milestone 2: CI (`.github/workflows/ci.yml`)

Runs on every pull request and every push to `main`:

| Job | What it proves |
|---|---|
| Gitleaks | No secrets committed, including in full git history |
| Build | `npm run typecheck` and `npm run build` for the frontend; `manage.py check` for Django |
| Trivy (fs) | Dependency and misconfiguration scan (report-only, see Tradeoffs) |
| Tests + Coverage | `pytest` against a **real Postgres 16 service container**. A failing test fails the workflow (verified with a deliberate `assert False`). |
| SonarCloud | Static analysis and coverage upload |
| Docker Build Check | The image builds on every PR, before anything is published |

On pull requests, every publish and deploy job is **skipped** (verified).

### Milestone 3: Publish to both registries

On push to `main` only:

- **Publish to ECR**
  - Authenticates with **GitHub OIDC**, so no AWS keys are stored anywhere.
  - Builds the image **once** and pushes it tagged `:<commit-sha>` and `:latest`.
  - Exports that same image with `docker save` and hands the tarball to the next job as a workflow artifact.
- **Publish to JFrog**
  - Uploads the tarball to a Generic repository in a self-hosted Artifactory, at `notesy/<commit-sha>/` and `notesy/latest/`.
  - Uses a push-scoped token belonging to a dedicated `ci-notesy` user, with rights on that one repository only.

### Milestone 4: Deploy (both paths built)

All infrastructure is Terraform in `infra/`. A `deploy_target` variable (`"ecs"` or `"eks"`, default `"eks"`) chooses which platform gets built. A matching `DEPLOY_TARGET` GitHub variable chooses which deploy job runs.

**Shared by both paths:**

- **Network:** a VPC across 2 AZs. Public subnets hold the load balancers and compute; private subnets hold RDS and have no internet route.
- **Database:** RDS Postgres 16 (`db.t3.micro`), encrypted, not publicly accessible. Only the app's security group can reach port 5432.
- **Secrets:** `DATABASE_URL` and `DJANGO_SECRET_KEY` are generated by Terraform and stored in Secrets Manager.
- **ECR and the GitHub deploy role** are part of the same stack, so `terraform destroy` removes everything billable. The deploy role is trusted only by `main` of this repo, and can push only to the notesy ECR repository.

**Path A: ECS Fargate** (`deploy_target = "ecs"`)

- A Fargate service behind an ALB, with a deployment circuit breaker and automatic rollback.
- Secrets are injected by ECS straight from Secrets Manager through the task definition's `secrets`, never as plain environment variables.
- IAM:
  - The execution role can read only the two notesy secrets.
  - The task role has no permissions.
  - The deploy role can update only the notesy service and pass only the two ECS roles.
- **Deploy to ECS** reads the current task definition, swaps **only** the image to `…/notesy:<commit-sha>`, registers a new revision, updates the service and waits for `services-stable`. The service has `ignore_changes = [task_definition, desired_count]`, so Terraform never reverts a deploy.

**Path B: Kubernetes on EKS** (`deploy_target = "eks"`)

- **Cluster:** EKS 1.37 with API-mode access entries, and a managed node group (`t3.medium`, 1–2 nodes) in the public subnets. Nodes pull from ECR with a read-only role. RDS accepts Postgres only from the cluster security group.
- **Access:** the cluster creator is admin. The GitHub deploy role gets **AmazonEKSEditPolicy scoped to the `notesy` namespace only**, plus `eks:DescribeCluster`. It can't touch the rest of the cluster.
- **Manifests (`k8s/`):**
  - `namespace.yaml`
  - `configmap.yaml`: non-secret config (`DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`)
  - `deployment.yaml`:
    - 1 replica, with a rolling update of `maxSurge 1` and `maxUnavailable 0`.
    - Config comes in via `envFrom` from the ConfigMap and the Secret.
    - Resource requests and limits are set; the pod runs as non-root with no privilege escalation.
    - Startup, readiness and liveness probes hit `/login/` with `Host: localhost`.
    - The image is the placeholder `__IMAGE__`, replaced at deploy time.
  - `service.yaml`: `type: LoadBalancer`, port 80 → 8000.
- **Secret:** `notesy-secrets` is created per session **from Secrets Manager values** with `kubectl create secret`. It's never written to a file and never in git.
- **Deploy to EKS:**
  1. Connects with `aws eks update-kubeconfig`.
  2. Applies the ConfigMap and Service from the repo.
  3. Substitutes `…/notesy:<commit-sha>` into the Deployment and applies it.
  4. Waits for `kubectl rollout status`. If the rollout fails, a follow-up step runs `kubectl rollout undo`.

**Verified on both paths:** the commit on `main`, the image tag in ECR, and the image actually running were the same SHA.

## 2. Tradeoffs

| Decision | Alternative | Why |
|---|---|---|
| **Compute in public subnets with public IPs, no NAT gateway** (ECS tasks, EKS nodes) | Private subnets + NAT gateway or VPC endpoints | A NAT gateway costs ~$30+/month even when idle. Security groups only admit traffic from the load balancer. |
| **One Terraform stack; `destroy` removes everything, including ECR** | A small persistent "bootstrap" stack for ECR and the pipeline role | No idle charges between sessions. The cost is that image history resets every session, and each session starts with `apply` plus a pipeline run. The role's ARN is stable because its name is fixed. |
| **`deploy_target` switch in one stack** | Separate stacks per platform | ECS and EKS share the VPC, RDS, ECR, secrets and the deploy role, so a switch avoids duplicating or importing them. Only one platform is billed at a time. |
| **Self-hosted Artifactory (OSS) with a Generic repo holding `docker save` tarballs** | JFrog Cloud, or JCR, with a real Docker registry | OSS can't host Docker repositories, and the Cloud free tier needed a company email. The tarball *is* the exact image in ECR and restores with `docker load`, but you can't `docker pull` it. |
| **Artifactory over plain HTTP** | TLS in front (e.g. `jfrog.<domain>` with a certificate) | Lab constraint. The push token travels unencrypted. Mitigations: the token can only touch `notesy-repo`, and it's rotatable. |
| **`ci-notesy` has Delete/Overwrite on `notesy-repo`** | SHA paths only, no `latest` in JFrog | Needed to replace `latest`. Keeping the same tags in both registries was the requirement. Scope is still limited to one repository. |
| **Deploy needs *both* publish jobs** | Deploy as soon as ECR succeeds | Nothing runs that isn't recoverable from either registry. The cost is that a JFrog outage blocks deploys. |
| **Migrations run in the entrypoint; 1 replica/task** | A one-off migration task or Kubernetes Job before the rollout | Simple and correct with one replica. With several starting at once, they'd race on migrations. |
| **EKS: Kubernetes Secret created from Secrets Manager by hand each session** | External Secrets Operator or the Secrets Store CSI driver syncing from Secrets Manager | No extra controllers to run. The cost is a manual step per session, and the pipeline can't rotate the secret. |
| **EKS: `type: LoadBalancer` Service (AWS-provisioned load balancer)** | AWS Load Balancer Controller + Ingress (ALB) | Works out of the box with no controller or extra IAM. It can't do path routing or TLS termination the way an Ingress can. |
| **EKS: `ALLOWED_HOSTS = .us-east-1.elb.amazonaws.com,localhost`** | The exact hostname, set after the Service exists | The load balancer's hostname isn't known until the Service is created. The leading-dot pattern avoids a two-pass deploy without falling back to `*`. A custom domain removes the need. |
| **EKS: probes send `Host: localhost`** | Adding the pod IP to `ALLOWED_HOSTS` via the downward API | No code change, and the probe spec documents the reason. |
| **EKS: public cluster API endpoint** | Private endpoint, or public restricted to known CIDRs | GitHub-hosted runners and a home laptop both need to reach it. Access is still gated by IAM and access entries. |
| **RDS `db.t3.micro`** | `db.t4g.micro` (Graviton, slightly cheaper) | `t4g` hit an AWS capacity shortage in us-east-1 (CURVEBALLS #18). |
| **Trivy is report-only (`exit-code: 0`)** | Fail on CRITICAL/HIGH | Avoids blocking on unfixed upstream CVEs during the build-out. It did hide `requests==2.20.0`, now upgraded. |
| **Sonar quality gate not awaited (`qualitygate.wait=false`)** | Fail the build on the gate | The gate failed on new-code coverage, which is app code rather than pipeline. Scanner errors still fail the job. |
| **`demo/demo` created on demand, never by the running service** | Seed on every start | No known password on a public URL unless deliberately created. |
| **Terraform state local and gitignored** | Remote state in S3 with locking | Single operator. State contains the generated DB password and secret key, so it must never be committed. |
| **`JFROG_URL` stored as a GitHub *variable*** | As a secret, as the guide lists it | A URL isn't sensitive. The token and username are secrets. |

## 3. How to run it

### Locally

```bash
docker compose up --build
```

Open http://localhost:8000 and log in as **demo / demo**. Migrations run automatically; nothing but Docker is needed on the host. To confirm the app is on Postgres:

```bash
docker compose exec db psql -U notesy -d notesy -c "\dt"
```

### CI/CD prerequisites (one-time)

- **GitHub Actions secrets:** `AWS_ECR_DEPLOY_ROLE_ARN`, `JFROG_ACCESS_TOKEN`, `JFROG_USERNAME`, `SONAR_TOKEN`
- **GitHub Actions variables:**
  - `DEPLOY_TARGET` (`eks` or `ecs`, matching Terraform's `deploy_target`)
  - `AWS_REGION`, `ECR_REPOSITORY`, `APP_NAME`
  - `EKS_CLUSTER` for EKS; `ECS_CLUSTER` and `ECS_SERVICE` for ECS
  - `JFROG_URL`, `JFROG_REPO`
  - `SONAR_ORGANIZATION`, `SONAR_PROJECT_KEY`
- **The GitHub OIDC provider** (`token.actions.githubusercontent.com`) must exist in the AWS account. Terraform reads it but never creates or destroys it.

`AWS_ECR_DEPLOY_ROLE_ARN` is `arn:aws:iam::<account-id>:role/notesy-github-deploy-role`. It doesn't change across destroy and apply.

### A working session on EKS (default)

```bash
# 1. Create the infrastructure (~15-20 min: EKS control plane, nodes, RDS)
cd infra
terraform apply                          # deploy_target defaults to "eks"
aws eks update-kubeconfig --region us-east-1 --name notesy-eks
kubectl get nodes                        # expect 1 node, Ready

# 2. Namespace, config and the Secret (from Secrets Manager, never written to disk)
cd ..
kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/configmap.yaml
DBURL=$(aws secretsmanager get-secret-value --secret-id notesy/DATABASE_URL --query SecretString --output text)
SKEY=$(aws secretsmanager get-secret-value --secret-id notesy/DJANGO_SECRET_KEY --query SecretString --output text)
kubectl -n notesy create secret generic notesy-secrets \
  --from-literal=DATABASE_URL="$DBURL" --from-literal=DJANGO_SECRET_KEY="$SKEY"
unset DBURL SKEY

# 3. Publish and deploy: push to main, or re-run the latest workflow.

# 4. Find the app, and optionally create demo/demo
kubectl get svc notesy -n notesy         # EXTERNAL-IP is the URL (allow 2-3 min)
kubectl exec -n notesy deploy/notesy -- python manage.py seed

# 5. Tear everything down when done (EKS, nodes, RDS and the load balancer all bill hourly)
kubectl delete svc notesy -n notesy      # lets Kubernetes remove its load balancer first
cd infra && terraform destroy
```

Deleting the Service before `terraform destroy` matters. Kubernetes created that load balancer, not Terraform, so if it's still attached, it can block the subnet and VPC deletion.

### A working session on ECS

```bash
cd infra
terraform apply -var deploy_target=ecs   # and set the DEPLOY_TARGET GitHub variable to "ecs"
# push to main (or re-run) to publish + deploy, then:
terraform output app_url
terraform destroy -var deploy_target=ecs
```

To create `demo/demo` on ECS, run `manage.py seed` as a one-off ECS task (`aws ecs run-task` with a command override).

## 4. Keeping two registries in sync

The pipeline publishes in a fixed order, and each step only runs if the previous one succeeded:

```
build once ─► push to ECR (:sha, :latest) ─► docker save ─► artifact ─► upload to JFrog (sha/, latest/) ─► deploy (ECS or EKS)
```

| What failed | State afterwards | Recovery |
|---|---|---|
| **ECR push** | Nothing published anywhere; nothing deployed | Fix the cause (usually auth) and re-run. Nothing to reconcile. |
| **JFrog upload, ECR succeeded** | ECR is one build ahead. JFrog's `latest` is stale. **Nothing is deployed**, because deploy needs both. | **Re-run failed jobs.** The JFrog job downloads the same tarball artifact (kept 1 day) and retries. No rebuild, no second ECR push, identical bytes. |
| **JFrog fails and the artifact has expired** | Same as above, after more than a day | Don't rebuild: a rebuild isn't byte-identical. Pull the image from ECR by SHA, `docker save` it, and upload it to the same JFrog paths. |
| **Deploy fails after both uploads** | Both registries agree. ECS: the circuit breaker rolled back. EKS: `rollout undo` ran. | Fix the cause and re-run the deploy job. |

**Why this design holds:**
- **Every step is safe to repeat.** Pushing the same tag to ECR, or re-uploading the same path to JFrog, just replaces it with identical content.
- **`curl --fail` makes every rejected upload fail the job.** This caught a real `403` that would otherwise have gone green with a stale `latest`.
- **Publishing across two registries can't be atomic.** The design ensures they can only diverge in one direction (ECR ahead), that divergence is visible as a failed job, and nothing is deployed until they agree again.

This actually happened: see CURVEBALLS.md #13.

## 5. Rollback

Every image is tagged with its commit SHA, and every deploy pins that SHA, either in an ECS task definition revision or in the Deployment's pod template.

### On EKS

**Automatic:** if the new pods don't become ready within 5 minutes, `kubectl rollout status` fails the job, and the pipeline runs `kubectl rollout undo`. Because `maxUnavailable` is 0, the old pod keeps serving throughout.

**Manual:**

```bash
# See the rollout history, and which image each revision ran
kubectl rollout history deployment/notesy -n notesy
kubectl rollout history deployment/notesy -n notesy --revision=<n>   # shows the image

# Go back one revision, or to a specific one
kubectl rollout undo deployment/notesy -n notesy
kubectl rollout undo deployment/notesy -n notesy --to-revision=<n>

# Or pin an exact known-good build by SHA
kubectl set image deployment/notesy -n notesy \
  notesy=<account>.dkr.ecr.us-east-1.amazonaws.com/notesy:<good-sha>
kubectl rollout status deployment/notesy -n notesy
```

### On ECS

**Automatic:** the deployment circuit breaker has `rollback = true`. If a new revision never passes the ALB health check, ECS returns to the last working revision, and the pipeline's `services-stable` wait fails the job.

**Manual:**

```bash
# See which image each recent revision runs
for rev in $(aws ecs list-task-definitions --family-prefix notesy --sort DESC \
               --max-items 5 --query "taskDefinitionArns[]" --output text); do
  echo "$rev  $(aws ecs describe-task-definition --task-definition "$rev" \
                 --query 'taskDefinition.containerDefinitions[0].image' --output text)"
done

# Point the service back at the revision with the good SHA
aws ecs update-service --cluster notesy-cluster --service notesy-service \
  --task-definition notesy:<good-revision>
aws ecs wait services-stable --cluster notesy-cluster --service notesy-service
```

### When the image is no longer in ECR

For example, after a `terraform destroy` reset the repository. JFrog is the source:

```bash
curl -fsSL -H "Authorization: Bearer $JFROG_TOKEN" \
  "$JFROG_URL/artifactory/notesy-repo/notesy/<sha>/notesy-<sha>.tar.gz" | gunzip | docker load
docker push <account>.dkr.ecr.us-east-1.amazonaws.com/notesy:<sha>
# then deploy that SHA as above
```

`docker load` restores the image under its original ECR name and tag, so it can be pushed straight back. In this lab, the JFrog server is also torn down between sessions, so this path only works within a session. A persistent registry is item 4 in section 6.

### Either platform

**Roll forward:** for anything non-urgent, `git revert` the bad commit and push. The pipeline builds, publishes and deploys a new SHA through the normal gates.

**Caveat: database migrations.** Rolling back the image doesn't roll back the schema. If the bad release ran a migration the previous code can't handle, write a reverse migration or roll forward instead. Keeping migrations backward-compatible for one release is the durable fix.

## 6. Deploy paths chosen, and what it would take for real users

**ECS Fargate first (Path A):** it built directly on the ECR + OIDC pipeline, uses managed services for everything stateful, and has no cluster to operate. It's the simplest correct way to run one container on AWS.

**EKS second (Path B, the extra-credit option):** it reuses the same image, pipeline, database and secrets, and proves the build is platform-independent. Only the deploy job and the manifests differ. The `deploy_target` switch keeps both paths one variable apart, and only one is billed at a time.

**Where it stands:** a correct, least-privilege, single-replica deployment on either platform that proves the pipeline end to end, sized and structured for a lab that is torn down after each session.

**What would need to change before trusting it with real users:**

1. **HTTPS and a real domain.**
   - ECS: an ACM certificate on the ALB.
   - EKS: the AWS Load Balancer Controller with an Ingress (ALB + ACM).
   - Either way: HTTP redirected to HTTPS, Django's secure-cookie and HSTS settings on, and `ALLOWED_HOSTS` set to the exact domain.
2. **Network:** compute in private subnets behind NAT or VPC endpoints for ECR, Secrets Manager, STS and CloudWatch. EKS: a private or CIDR-restricted API endpoint.
3. **Database:** Multi-AZ RDS, deletion protection, a final snapshot on delete, and retained backups. Let RDS manage the master password so it never enters Terraform state.
4. **A persistent bootstrap stack** for ECR, the pipeline role and remote Terraform state (S3 with locking), so image history and rollback targets survive infrastructure teardown.
5. **Migrations** as a one-off ECS task or a Kubernetes Job run by the pipeline before the rollout, not on every container start. That unblocks the next item.
6. **Scale and resilience:**
   - At least 2 replicas across AZs, with autoscaling (ECS target tracking, or a Kubernetes HPA plus a PodDisruptionBudget).
   - A second node for EKS.
   - Alarms on 5xx rates, unhealthy targets and RDS CPU and storage.
7. **EKS specifics:**
   - Sync secrets from Secrets Manager with External Secrets or the CSI driver, instead of a manual `kubectl create secret`.
   - Use EKS Pod Identity if the app ever needs AWS APIs.
   - Add NetworkPolicies to restrict pod-to-pod traffic.
   - Use Pod Security Admission at the `restricted` level.
8. **The summarize endpoint:** move slow work off the request path (a background queue), or at least set client timeouts on outbound calls, so slow requests can't exhaust worker threads.
9. **The artifact registry:** JFrog Cloud or JCR behind TLS with a real Docker repository, so both registries can be `docker pull`ed.
10. **Security gates that block:** Trivy failing on CRITICAL, the Sonar quality gate enforced, and pinned Python dependencies.
11. **Housekeeping:**
    - Remove the unused workflow variables (Vault, `JAVA_VERSION`), unused `python-dotenv`, and the ECS IAM roles that are created even on EKS.
    - Bump GitHub Actions to Node 24 versions.
    - Add `.gitattributes` to force LF endings on `*.sh`.
