# Deploying Notesy

Notesy is a small Django + HTMX notes app. This document covers how it goes from a commit on `main` to a running service on AWS ECS Fargate, the decisions made along the way, and how to operate it.

For everything that broke during the build and how it was diagnosed, see [CURVEBALLS.md](CURVEBALLS.md).

---

## 1. What was built

### Milestone 1: Containerize

- **Multi-stage `Dockerfile`**
  - Stage 1 (Node 20) typechecks and builds the TypeScript bundle.
  - Stage 2 (Python 3.12 slim) runs the app. Node isn't in the final image.
  - The app runs as a non-root user (`app`, uid 1000).
  - `collectstatic` runs at build time so WhiteNoise can serve static files.
- **`entrypoint.sh`**
  - Runs `migrate` on every container start, then `exec`s the command, so gunicorn gets stop signals directly.
  - Migrations live in the image, so they run the same way under Compose and ECS.
- **`.dockerignore`** keeps `.env`, `.git`, local builds and SQLite files out of the image.
- **`docker-compose.yml`**
  - App plus Postgres 16, with a `pg_isready` healthcheck. The app waits for `service_healthy`.
  - Seeding the `demo/demo` user is local-only.
- **`notesy/settings.py` (ticket NOTESY-101)**
  - Config comes from the environment: `DJANGO_SECRET_KEY`, `DJANGO_DEBUG` (off by default), `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, `DATABASE_URL`.
  - With `DEBUG` off, the app refuses to start if the secret key or database URL is missing, so misconfiguration fails loudly instead of silently falling back to SQLite.
  - Sessions are stored in the database.
- **Gunicorn** runs `gthread` workers (3 workers × 4 threads), so idle or slow connections don't block a whole worker.

### Milestone 2: CI (`.github/workflows/ci.yml`)

Runs on every pull request and every push to `main`:

| Job | What it proves |
|---|---|
| Gitleaks | No secrets committed, including in full git history |
| Build | `npm run typecheck` and `npm run build` for the frontend; `manage.py check` for Django |
| Trivy (fs) | Dependency and misconfiguration scan (report-only, see Tradeoffs) |
| Tests + Coverage | `pytest` against a **real Postgres 16 service container**. A failing test fails the workflow (verified with a deliberate `assert False`). |
| SonarCloud | Static analysis and coverage upload |
| Docker Build Check | The image builds on every PR, before anything is published |

### Milestone 3: Publish to both registries

On push to `main` only:

- **Publish to ECR**
  - Authenticates with **GitHub OIDC**, so no AWS keys are stored anywhere.
  - Builds the image **once** and pushes it tagged `:<commit-sha>` and `:latest`.
  - Exports that same image with `docker save` and hands the tarball to the next job as a workflow artifact.
- **Publish to JFrog**
  - Uploads the tarball to a Generic repository in a self-hosted Artifactory, at `notesy/<commit-sha>/` and `notesy/latest/`.
  - Uses a push-scoped token belonging to a dedicated `ci-notesy` user, with rights on that one repository only.

### Milestone 4: Deploy (Path A, ECS Fargate)

All infrastructure is Terraform in `infra/`:

- **Network:** a VPC across 2 AZs. Public subnets hold the ALB and tasks; private subnets hold RDS and have no internet route. Security groups chain internet → ALB :80 → app :8000 → Postgres :5432.
- **Database:** RDS Postgres 16 (`db.t4g.micro`), encrypted, not publicly accessible.
- **Secrets:** `DATABASE_URL` and `DJANGO_SECRET_KEY` are generated by Terraform, stored in Secrets Manager, and injected by ECS through `secrets`. They're never in the image or plain environment variables.
- **ECS:** a Fargate service behind an ALB, with a deployment circuit breaker and automatic rollback.
- **IAM:**
  - The execution role can read only the two notesy secrets.
  - The task role has no permissions (the app doesn't call AWS).
  - The GitHub deploy role is trusted only by `main` of this repo. It can push only to the notesy ECR repository, update only the notesy service, and pass only the two ECS roles.
- **ECR:** the repository and the GitHub deploy role are part of the same stack, so `terraform destroy` removes everything billable.

The **Deploy to ECS** job runs after both registries have the image:

1. Reads the current task definition.
2. Swaps **only** the image, to `…/notesy:<commit-sha>`.
3. Registers a new revision, updates the service (scaling it to 1), and waits for `services-stable`.

Terraform owns the configuration; the pipeline owns which build runs. The service has `ignore_changes = [task_definition, desired_count]`, so Terraform never reverts a deploy.

**Verified:** the commit on `main`, the ECR tag, and the image in the running task definition were the same SHA.

## 2. Tradeoffs

| Decision | Alternative | Why |
|---|---|---|
| **Tasks in public subnets with public IPs, no NAT gateway** | Private subnets + NAT gateway or VPC endpoints | A NAT gateway costs ~$30+/month even when idle. The tasks' security group only accepts traffic from the ALB, so they aren't reachable directly. |
| **One Terraform stack; `destroy` removes everything, including ECR** | A small persistent "bootstrap" stack for ECR and the pipeline role | No idle charges between sessions. The cost is that image history resets every session, and each session starts with `apply` plus a pipeline run. The role's ARN is stable because its name is fixed. |
| **Self-hosted Artifactory (OSS) with a Generic repo holding `docker save` tarballs** | JFrog Cloud, or JCR, with a real Docker registry | OSS can't host Docker repositories, and the Cloud free tier needed a company email. The tarball *is* the exact image in ECR and restores with `docker load`, but you can't `docker pull` it. |
| **Artifactory over plain HTTP** | TLS in front (e.g. `jfrog.<domain>` with a certificate) | Lab constraint. The push token travels unencrypted. Mitigations: the token can only touch `notesy-repo`, and it's rotatable. |
| **`ci-notesy` has Delete/Overwrite on `notesy-repo`** | SHA paths only, no `latest` in JFrog | Needed to replace `latest`. Keeping the same tags in both registries was the requirement. Scope is still limited to one repository. |
| **Deploy needs *both* publish jobs** | Deploy as soon as ECR succeeds | Nothing runs that isn't recoverable from either registry. The cost is that a JFrog outage blocks deploys. |
| **Migrations run in the entrypoint** | A one-off migration task before the service update | Simple and correct with one task. With several tasks starting together, they'd race on migrations. |
| **Trivy is report-only (`exit-code: 0`)** | Fail on CRITICAL/HIGH | Avoids blocking on unfixed upstream CVEs during the build-out. It did hide `requests==2.20.0`, now upgraded. |
| **Sonar quality gate not awaited (`qualitygate.wait=false`)** | Fail the build on the gate | The gate failed on new-code coverage, which is app code rather than pipeline. Scanner errors still fail the job. |
| **`demo/demo` created by a one-off task, `run_seed=false` by default** | Seed on every start | No known password on a public URL unless deliberately created. |
| **`ALLOWED_HOSTS` = ALB DNS + the task's own IP from ECS metadata** | `ALLOWED_HOSTS = ["*"]` | `*` disables host-header protection. Reading the task IP keeps health checks working without it. |
| **Terraform state local and gitignored** | Remote state in S3 with locking | Single operator. State contains the generated DB password and secret key, so it must never be committed. |
| **`JFROG_URL` stored as a GitHub *variable*** | As a secret, as the guide lists it | A URL isn't sensitive. The token and username are secrets. |

## 3. How to run it

### Locally

```bash
docker compose up --build
```

Open http://localhost:8000 and log in as **demo / demo**. Migrations run automatically; nothing but Docker is needed on the host. To confirm the app is on Postgres:

```bash
docker compose exec db psql -U notesy -d notesy -c "\dt"
```

### CI/CD prerequisites (one-time)

- **GitHub Actions secrets:** `AWS_ECR_DEPLOY_ROLE_ARN`, `JFROG_ACCESS_TOKEN`, `JFROG_USERNAME`, `SONAR_TOKEN`
- **GitHub Actions variables:** `AWS_REGION`, `ECR_REPOSITORY`, `ECS_CLUSTER`, `ECS_SERVICE`, `APP_NAME`, `JFROG_URL`, `JFROG_REPO`, `SONAR_ORGANIZATION`, `SONAR_PROJECT_KEY`
- **The GitHub OIDC provider** (`token.actions.githubusercontent.com`) must exist in the AWS account. Terraform reads it but never creates or destroys it.

`AWS_ECR_DEPLOY_ROLE_ARN` is `arn:aws:iam::<account-id>:role/notesy-github-deploy-role`. It doesn't change across destroy and apply.

### A working session on AWS

```bash
# 1. Create the infrastructure (~10 min, mostly RDS). The service starts at 0 tasks.
cd infra
terraform apply

# 2. Publish and deploy: push to main, or re-run the latest workflow.
#    The pipeline pushes to ECR + JFrog, then deploys that SHA and scales to 1.

# 3. (Optional) create demo/demo on the deployed app
TASKDEF=$(aws ecs describe-services --cluster notesy-cluster --services notesy-service \
  --query "services[0].taskDefinition" --output text)
APP_SG=$(aws ec2 describe-security-groups --filters Name=group-name,Values=notesy-app-sg \
  --query "SecurityGroups[0].GroupId" --output text)
SUBNETS=$(terraform output -json public_subnet_ids | tr -d '[]" ')
aws ecs run-task --cluster notesy-cluster --launch-type FARGATE --task-definition "$TASKDEF" \
  --network-configuration "awsvpcConfiguration={subnets=[$SUBNETS],securityGroups=[$APP_SG],assignPublicIp=ENABLED}" \
  --overrides '{"containerOverrides":[{"name":"notesy","command":["python","manage.py","seed"]}]}'

# 4. Open the app
terraform output app_url

# 5. Tear everything down when done. RDS and the ALB bill by the hour.
terraform destroy
```

## 4. Keeping two registries in sync

The pipeline publishes in a fixed order, and each step only runs if the previous one succeeded:

```
build once ─► push to ECR (:sha, :latest) ─► docker save ─► artifact ─► upload to JFrog (sha/, latest/) ─► deploy
```

| What failed | State afterwards | Recovery |
|---|---|---|
| **ECR push** | Nothing published anywhere; nothing deployed | Fix the cause (usually auth) and re-run. Nothing to reconcile. |
| **JFrog upload, ECR succeeded** | ECR is one build ahead. JFrog's `latest` is stale. **Nothing is deployed**, because deploy needs both. | **Re-run failed jobs.** The JFrog job downloads the same tarball artifact (kept 1 day) and retries. No rebuild, no second ECR push, identical bytes. |
| **JFrog fails and the artifact has expired** | Same as above, after more than a day | Don't rebuild: a rebuild isn't byte-identical. Pull the image from ECR by SHA, `docker save` it, and upload it to the same JFrog paths. |
| **Deploy fails after both uploads** | Both registries agree; the service is unchanged, or the circuit breaker rolled it back | Fix the cause and re-run the deploy job. |

**Why this design holds:**
- **Every step is safe to repeat.** Pushing the same tag to ECR, or re-uploading the same path to JFrog, just replaces it with identical content.
- **`curl --fail` makes every rejected upload fail the job.** This caught a real `403` that would otherwise have gone green with a stale `latest`.
- **Publishing across two registries can't be atomic.** The design ensures they can only diverge in one direction (ECR ahead), that divergence is visible as a failed job, and nothing is deployed until they agree again.

This actually happened: see CURVEBALLS.md #13.

## 5. Rollback

Every image is tagged with its commit SHA, and every deploy registers a new task definition revision pinned to that SHA.

**Automatic:** the ECS deployment circuit breaker has `rollback = true`. If a new revision never passes the ALB health check, ECS returns the service to the last working revision, and the pipeline's `services-stable` wait fails the job.

**Manual, to a known-good build:**

```bash
# See which image each recent revision runs
for rev in $(aws ecs list-task-definitions --family-prefix notesy --sort DESC \
               --max-items 5 --query "taskDefinitionArns[]" --output text); do
  echo "$rev  $(aws ecs describe-task-definition --task-definition "$rev" \
                 --query 'taskDefinition.containerDefinitions[0].image' --output text)"
done

# Point the service back at the revision with the good SHA
aws ecs update-service --cluster notesy-cluster --service notesy-service \
  --task-definition notesy:<good-revision>
aws ecs wait services-stable --cluster notesy-cluster --service notesy-service
```

This reuses an image already in ECR. Nothing is rebuilt, so what comes back is exactly what ran before.

**If the image is no longer in ECR** (for example, after a `terraform destroy` reset the repository), JFrog is the source:

```bash
curl -fsSL -H "Authorization: Bearer $JFROG_TOKEN" \
  "$JFROG_URL/artifactory/notesy-repo/notesy/<sha>/notesy-<sha>.tar.gz" | gunzip | docker load
docker push <account>.dkr.ecr.us-east-1.amazonaws.com/notesy:<sha>
# then register a revision with that image, as the deploy job does, and update the service
```

`docker load` restores the image under its original ECR name and tag, so it can be pushed straight back.

**Roll forward:** for anything non-urgent, `git revert` the bad commit and push. The pipeline builds, publishes and deploys a new SHA through the normal gates.

**Caveat: database migrations.** Rolling back the image doesn't roll back the schema. If the bad release ran a migration the previous code can't handle, write a reverse migration or roll forward instead. Keeping migrations backward-compatible for one release is the durable fix.

## 6. Deploy path chosen, and what it would take for real users

**Why ECS Fargate (Path A):** it builds directly on the ECR + OIDC pipeline, uses managed services for everything stateful (RDS, Secrets Manager), and has no cluster to operate. The Kubernetes path (EKS) is planned as a separate exercise using the same image and pipeline.

**Where it stands:** a correct, least-privilege, single-task deployment that proves the pipeline end to end, sized and structured for a lab that is torn down after each session.

**What would need to change before trusting it with real users:**

1. **HTTPS:** an ACM certificate and a real domain on the ALB, HTTP redirected to HTTPS, with Django's secure-cookie and HSTS settings on.
2. **Network:** tasks in private subnets behind NAT or VPC endpoints for ECR, Secrets Manager and CloudWatch; no public IPs on tasks.
3. **Database:** Multi-AZ RDS, deletion protection, a final snapshot on delete, and retained backups. Let RDS manage the master password so it never enters Terraform state.
4. **A persistent bootstrap stack** for ECR, the pipeline role and remote Terraform state (S3 with locking), so image history and rollback targets survive infrastructure teardown.
5. **Migrations** as a one-off ECS task run by the pipeline before the service update, not on every container start.
6. **Scale and resilience:** at least 2 tasks across AZs, target-tracking autoscaling, and CloudWatch alarms on 5xx rates, unhealthy targets and RDS CPU and storage.
7. **The summarize endpoint:** move slow work off the request path (a background queue), or at least set client timeouts on outbound calls, so slow requests can't exhaust worker threads.
8. **The artifact registry:** JFrog Cloud or JCR behind TLS with a real Docker repository, so both registries can be `docker pull`ed.
9. **Security gates that block:** Trivy failing on CRITICAL, the Sonar quality gate enforced, and pinned Python dependencies.
10. **Housekeeping:** remove the unused workflow variables (Vault, `JAVA_VERSION`) and unused `python-dotenv`, bump GitHub Actions to Node 24 versions, and add `.gitattributes` to force LF endings on `*.sh`.
